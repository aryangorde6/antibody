# The last two runner commands, and a CI workflow.

1. `ledger <name>`
   Joins candidates.json, results.json, probes/, proofs/, and curated.json and explanations.json when they exist, into `ledger.json`, and renders a static page.
   - curated.json maps each sha to `{"verdict": "BUG" or "NOT-A-BUG", "reason", "link"}`. explanations.json maps each sha to one plain-English line. A row with no line shows its commit subject. Both are written later, during an audit, so pin these formats in the code and in `tests/test_gate.py`.
   - Before writing anything, it re-runs `prove` for every row that has a proof. Only rows it has just proved again count as NOW CAUGHT.
   - Statuses: CAUGHT (an existing test catches it); NOW CAUGHT (a new test, just re-proven); STILL EXPOSED (put back, every test green, and the probe shows a change, or no check could show one either way; the row says which); NO CHANGE FOUND (listed under "Excluded after a check", with the check and both outputs); NO DATA (with its reason); NOT A BUG (from curation, with its reason); EXCLUDED (with its reason).
   - The page, plain HTML and CSS plus a little inline JavaScript, no build step, light and dark, no sideways scrolling at 375 px. Judges use it as the application, so it must be interactive, and still readable with JavaScript off:
     - the question at the top: "Of the bugs this project already fixed, how many could come back without a test noticing?"
     - one line: "Before: X of Y caught. After: X' of Y caught.", with Y (caught + escaped rows) explained in words right under it;
     - one row per past bug: status, one plain-English line, the fix commit linked to the project's public repository, the linked issue, and, when expanded, the evidence (catching test IDs, the new test's code, the probe outputs);
     - filter buttons by status, each with its count, and a text box that filters rows by subject or sha;
     - "Run it on your own project": the three commands, copyable;
     - the method in a few lines, and "What this can't tell you": rows with no data are unknown, never safe; "caught" means a test noticed, not that the test is perfect.
   - Never show commit author names, emails or commit message bodies. Subjects only.
   - Refuse to render if the number of rows differs from the number of candidates. If nothing could be checked, the line says "No past bug could be re-checked on today's code", never "0 of 0".
   - Record in ledger.json the sha-256 of curated.json with its timestamp, next to the time of the first `run`, so anyone can see curation happened before any result existed.
   - `ledger` always writes ledger.json and the page into `.antibody/<name>/`. With `--publish` it also copies ledger.json and every proven test into `audits/<name>/` (`targets/` is gitignored), writes the page to `site/<name>/index.html`, and rebuilds `site/index.html` with a link to each folder in `audits/`. `site/` is what gets deployed. Only a finished audit gets published. The sqlparse-ref run below only checks the runner, so don't publish it.

2. `gate <name>`, for CI, with no Bob involved. Reads ledger.json.
   - For every CAUGHT and NOW CAUGHT row: each catching test must be collected and pass at the current code, then be collected and fail with the bug put back. A catching test that's gone fails the gate by name: "catching test missing: <id>". Rows caught through a collection error or a timeout have no test IDs, so run the full suite and expect that same kind of failure. Never run an empty test list as-is.
   - If a patch no longer applies, warn "re-audit needed: <sha>" and don't fail. A refactor isn't a regression.
   - Every STILL EXPOSED row must be listed in `antibody-accepted.yaml` with a real sentence of reason (not empty, not "TODO"). Entries whose sha isn't STILL EXPOSED are a warning (stale).
   - Pin the format of `antibody-accepted.yaml`: a list of entries, each `- sha: <full sha>` then `  reason: <one sentence>` on the next line, nothing else. Parse it with the standard library (a few lines of line-by-line parsing), never `import yaml`: this laptop's `python3` has PyYAML, CI's Python 3.12 doesn't, so the tests would pass here and the gate would crash in CI. Reject a file that doesn't match the format, naming the line.
   - Fail if zero rows were checked.
   - Never write `antibody-accepted.yaml` yourself: accepting an exposure is the maintainer's decision. On sqlparse-ref the gate should fail on its STILL EXPOSED rows, which is the rule working.
   - Always end with: "checked X of Y; Z need re-audit; W accepted exposures".

3. `.github/workflows/antibody.yml`: on push and pull request, for each folder in `audits/`: set up Python 3.12, install uv (`python -m pip install uv`: GitHub's Ubuntu image has no uv, and `setup` needs it), run `setup` with the git URL, HEAD and `--deps` recorded in `.antibody/<name>/setup.json` (fail if that HEAD differs from ledger.json's), copy the proven tests from `audits/<name>/` into `targets/<name>/tests/antibody/`, and run `gate`. If `audits/` is empty, fail: nothing checked is never a pass.

In tomlkit, two saved subjects run on into the body and end with a `Signed-off-by:` line holding a maintainer's name and email address. Keep only the first line of the message as the subject, and never write anything from a `Signed-off-by:` line or any other trailer that names a person.
